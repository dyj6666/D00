# 重点问题复盘模板（硬性规定）

> 适用：凡在开发/验证中**需要多步排查、曾误导方向、或修复后仍需工程权衡**的问题，
> 必须按本模板完整记录到对应 `ENGINEERING_LOG.md`。
>
> **分析过程与排查思路是最重要的内容**——禁止只写"现象 + 根因 + 解决"三行结论。
> 后人（或几个月后的自己）靠的是排查路径，不是结论。

---

## 模板（每条问题按此填写）

### N.1 问题一句话标题

- **现象**：可观察到的故障表现，附关键日志/数据/数值（越具体越好）
- **影响面**：影响哪些功能、模式、场景
- **排查思路**：动手前先写方法论——怀疑哪几块、用什么手段切分（对照实验/打点/
  复现步骤/查配置/查文档），以及为什么这样切
- **排查过程**（按时间顺序，每步：做了什么 → 观察到什么 → 推断出什么）：
  1. 第一步：假设 X → 实验 → 证据 → 结论
  2. 第二步：假设 Y → 实验 → 证据 → 结论
  - **被推翻的方向也必须记录**（附证据），防止后人重复踩
- **根因**：最终定位的根本原因 + 机理（一句话讲清"为什么"）
- **解决方案**：改了什么（文件/函数/参数/配置），为什么这样改有效
- **验证**：修复后如何证明（复测数据、日志、全流程结果）
- **经验沉淀**：以后如何更快定位/避免同类问题（可复用方法、检查清单）

---

## 填写要求

1. **现象必须带证据**：日志原文、数值、截图，禁止模糊描述。
2. **每步排查必须写"为什么做这个实验"**：排除法/对照法/二分法的逻辑要可见。
3. **错误方向是宝藏**：记录"当时以为 X，实测是 Y"，比只写正确答案更有价值。
4. **根因写机理**：如"CRC 多项式非线性导致分段 XOR≠整段"，而非"CRC 算错了"。
5. **验证要可复现**：写修复后的复测数据，能跑出同样结论。
6. 模板放在 `docs\ISSUE_POSTMORTEM_TEMPLATE.md`，工程日志引用即可，不必重复粘贴。
