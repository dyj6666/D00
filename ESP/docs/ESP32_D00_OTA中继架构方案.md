# ESP32-S3 作为 OTA 中继：D00 固件无线透传升级架构方案

> 版本：v1.0（方案评审稿）｜ 日期：2026-09-29
> 目标：**PC 无线（WiFi）上传固件 → ESP32-S3 中继 → STM32F407 完成 OTA**，
> 速度 / 安全 / 稳定三项达到工业级水平
> 状态：**仅架构设计，尚未实现**（本文档为实施依据）

---

## 0. 一句话方案

> PC 通过 **WiFi** 上传「已加密+签名」的固件包 → **ESP32-S3 整包缓存（PSRAM 双缓冲）+ SHA256 完整性校验**
> → ESP32 以 **HOSTLINK 主端**身份经 **USART6（PC6/PC7）** 向 STM32 完成 OTA（含滑动窗口与断点续传）
> → STM32 复位进 BOOT，**BOOT 六道安全关**验证后安装并置 PENDING
> → ESP32 回读启动确认结果 → 上报 PC。

核心思想：**链路只负责"可靠搬运"，安全交给既有信任根（BOOT 的 ECDSA/AES 链）**——中继器不接触任何密钥。

## 1. 设计目标与硬约束

### 1.1 三大目标（可量化）

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| **速度** | 端到端 ≥ **150 KB/s**（目标 190 KB/s） | 300KB 包 ≈ 2s，900KB 包 ≈ 5s |
| **安全** | **8 道防线**，中继器零密钥持有 | 复用 BOOT 既有信任根，链路加完整性+鉴权 |
| **稳定** | 断线可续、掉电可恢复、任一环节失败不砖机 | 三级断点续传 + 事务化暂存 |

### 1.2 硬约束（来自两侧现状，不可绕开）

| 约束 | 来源 | 影响 |
| --- | --- | --- |
| HOSTLINK 帧格式固定 | `protocol.h`：`AA 55 cmd len payload CRC16-MODBUS` | ESP32 主端必须严格实现 |
| 数据块上限 **240 B**、单帧 ≤ **256 B** | `app_config.h: OTA_CHUNK_MAX/HOSTLINK_TX_FRAME_MAX` | 窗口化需在帧层做 |
| OTA 命令码固定 0x08~0x0D | `protocol.h` | 中继协议须与之共存 |
| UART OTA 为**逐块顺序 ACK**（`offset` 必须等于已收字节） | `ota_agent.c: Ota_Data` | 提速只能靠窗口+流控 |
| BOOT 安全链不可改 | `security.c` 六道关 | 中继器无需重复校验签名（但可选做预检） |
| **USART6(PC6/PC7) 已预留但未接入** | `pinout.h` 注释 + `bsp_uart.h` 仅 2 通道 | **D00 侧需改动**（见 §11） |
| **USART6/PC6 当前被信号发生器占用** | `signal_gen.c: SG_UART=USART6` | 二者互斥，需让位或时分复用 |

### 1.3 固件包与分区（既有事实）

```
OTA 包 = [ ota_header_t 32B ][ AES-256-CTR 密文 ][ ECDSA 签名 64B ]   magic=0x4F5441FE
          含: version / firmware_size / aes_iv(12B) / chip_id / build_no
STM32 分区: BOOT 64K@0x08000000 | RUN 832K@0x08010000 | PARAM 128K@0x080E0000
外部 W25Q128: ota_dl 1MB(下载槽) | img_lib 2MB(备份/回滚槽)
APP 上限 832KB → 实包约 300KB ~ 900KB（含头与签名）
```

- STM32/BOOT：**安全验证与安装**（唯一信任根）

## 3. 工作模式设计（核心决策）

### 3.1 三种模式对比

| 维度 | **A. 纯字节透传** | **B. 智能中继（推荐）** | **C. 混合自适应** |
| --- | --- | --- | --- |
| 原理 | PC 的 HOSTLINK 帧原样转发，ESP32 不解析协议 | ESP32 整包收完+校验后，自己作主端完成 OTA | 默认 B，链路异常时降级 A |
| PC 断线容忍 | ❌ 断线即失败（需 PC 全程在线） | ✅ **可断线**（ESP32 离线续传） | ✅ |
| 离线升级（SD 卡） | ❌ | ✅ | ✅ |
| 断点续传能力 | 依赖 PC 重试 | ✅ **三级续传**（PC↔ESP32 / ESP32↔STM32 / 掉电） | ✅ |
| 速度 | 受 PC↔ESP32 RTT 叠加影响 | ✅ **最优**（本地窗口+流控） | ✅ |
| 协议演进影响 | ✅ 固件协议变了 ESP32 不用改 | ⚠️ 需同步维护主端状态机 | ⚠️ |
| 实现复杂度 | 低（~500 行） | 中（~2000 行） | 高 |
| 工业级契合度 | 一般 | **最佳** | 好 |

### 3.2 推荐：**以 B 为主模式 + 保留 A 作为调试旁路**

理由：
1. **store-and-forward 是工业级传输的根本**：先完整接收+校验，再原子化转发——避免"边收边传"导致的半途耦合失败
2. **ESP32 有 8MB PSRAM**：整包缓存（≤900KB）绰绰有余——这是本方案能用模式 B 的硬件前提
3. **断线容忍**：现场 WiFi 不稳定是常态，模式 B 让升级过程与 PC 解耦
4. **保留模式 A**：用于链路调试、协议验证、以及"ESP32 固件有问题但 PC 直连可用"的应急场景

**关键设计原则**：
- **单向依赖**：`relay_core` 不依赖具体接入方式（TCP/HTTP/SD 均可驱动同一状态机）
- **零拷贝**：TCP 收到的数据直接落在 PSRAM 目标偏移，避免多级 memcpy（ESP32-S3 PSRAM 带宽是瓶颈之一）
- **无密钥**：ESP32 全程不接触私钥/AES 密钥，只做完整性与协议搬运

## 5. 协议设计

### 5.1 ESP32 ↔ PC：RelayLink（HOSTLINK 帧格式扩展，保持一致性）

复用 `AA 55 cmd len payload CRC16` 帧格式，命令码取 **0x20 段**（避开 D00 已用的 0x01~0x0D）：

| cmd | 名称 | 方向 | payload | 语义 |
| --- | --- | --- | --- | --- |
| 0x20 | `HELLO` | PC→ESP32 | proto_ver(2) + caps(4) | 能力协商（协议版本/窗口大小/是否支持SHA256） |
| 0x21 | `AUTH` | PC→ESP32 | token(16) / challenge-resp | 鉴权（可选，见 §8） |
| 0x22 | `PKG_BEGIN` | PC→ESP32 | size(4) + version(4) + build(4) + sha256(32) + name_len | 声明包元信息与**整包摘要**（用于收完比对） |
| 0x23 | `PKG_DATA` | PC→ESP32 | offset(4) + data(≤1024) | 分块上传（大块，千字节级） |
| 0x24 | `PKG_QUERY` | PC→ESP32 | — | 查询已收字节（断线重连后决定续传点） |
| 0x25 | `PKG_COMMIT` | PC→ESP32 | — | 提交（触发 SHA256 比对 → 进入 STAGED） |
| 0x26 | `OTA_START` | PC→ESP32 | mode(1) + window(1) | 指令 ESP32 开始向 STM32 转发（可指定模式 A/B） |
| 0x27 | `OTA_PROGRESS` | ESP32→PC | state(1) + sent(4) + total(4) + speed(4) + retry(2) | 进度上报（周期 200~500ms） |
| 0x28 | `OTA_ABORT` | 双向 | reason(1) | 中止（PC 主动 / ESP32 内部错误） |
| 0x7F | `ACK/NACK` | 双向 | ack_cmd(1) + status(1) + detail(2) | 统一应答（窗口化时支持批量 ACK） |

**要点**：
- **大块上传**：PC→ESP32 用 **1024B/块**（不受 D00 的 240B 限制，因为这是 ESP32 自己的协议）；
  ESP32→STM32 再按 240B 切片——**两段解耦，各用最优块长**
- 支持**窗口化 ACK**（PC 可连发 N 块，ESP32 批量确认）→ 上传段吞吐拉满
- 帧格式与 D00 一致 → 上位机可复用 `hostlink.py` 的 CRC16/FrameParser 代码

### 5.2 ESP32 ↔ STM32：HOSTLINK 原生 OTA（**语义零改动**）

直接复用 D00 既有命令，ESP32 扮演 `ota_hostlink_cli.py` 的角色：

```
CMD_OTA_BEGIN(0x08)  version(4)+size(4)         → 状态码
CMD_OTA_DATA(0x09)   offset(4)+data(≤240B)      → 状态码 + 已收字节(4)   ← 逐块 ACK
CMD_OTA_STATUS(0x0B) —                          → 状态(1)+已收(4)+总长(4) ← 续传协商
CMD_OTA_END(0x0A)    —                          → 状态码（随后复位）
CMD_OTA_RESET(0x0D)  —                          → 强制清会话（--no-resume 语义）
```

> ✅ **优势：D00 的 OTA 逻辑、安全链、断点续传槽、回滚机制全部原样复用，零语义改动。**

### 5.3 三层校验链（各司其职，互不替代）

| 层 | 机制 | 责任方 | 防什么 |
| --- | --- | --- | --- |
| L1 帧级 | CRC16-MODBUS | 每跳各自校验 | 线路误码 |
| L2 包级 | **SHA256 整包摘要**（PC 声明 vs ESP32 实算） | ESP32 | 传输截断/篡改/Flash 静默错误 |
| L3 密码级 | **ECDSA 验签 + AES-CTR 解密 + UID 绑定 + build_no 防重放** | **BOOT**（信任根） | 伪造包/跨芯片/重放/降级 |

## 6. 数据流时序

### 6.1 正常流程（模式 B）

```
PC                     ESP32                          STM32(APP)      STM32(BOOT)
│ PKG_BEGIN(size,sha)   │                                │                │
├──────────────────────►│ 预检(≤832KB? build_no>当前?)    │                │
│◄──────ACK─────────────┤                                │                │
│ PKG_DATA ×N (1KB,窗口) │ ──► PSRAM 落盘 + 流式 SHA256   │                │
├──────────────────────►│                                │                │
│◄─── 批量 ACK ─────────┤                                │                │
│ PKG_COMMIT            │ SHA256 比对 ✓ → STAGED         │                │
├──────────────────────►│                                │                │
│◄──────ACK─────────────┤                                │                │
│ OTA_START(mode=B)     │                                │                │
├──────────────────────►│ BEGIN(v,size) ────────────────►│ 擦外部 ota_dl  │
│                       │◄──────────────── 状态码 ────────┤                │
│                       │ STATUS ───────────────────────►│ 查续传点        │
│                       │◄──────────── state,rx,total ───┤                │
│                       │ DATA(窗口8×240B) ─────────────►│ 写外部槽        │
│                       │◄──────────── 逐块 ACK ─────────┤                │
│ OTA_PROGRESS(周期)     │                                │                │
│◄──────────────────────┤ END ──────────────────────────►│ 写 UPGRADE     │
│                       │                                │ → 复位          │
│                       │                                │        ┌───────┴──────┐
│                       │                                │        │ 六道安全关     │
│                       │                                │        │ 备份→解密写    │
│                       │                                │        │ →PENDING→复位  │
│                       │◄───── UART 捕获 BOOT 日志 ──────┼────────┤ (可选解析)     │
│                       │ (也可经 COM14 监视口独立观察)     │        └──────────────┘
│                       │ 探测: APP 在线? (:HOSTLINK STATUS)│ 新 APP 启动确认 │
│ OTA_PROGRESS(DONE)     │                                │                │
│◄──────────────────────┤                                │                │
```

### 6.2 断线重连（PC 侧）

```
① PC 重连 → PKG_QUERY → ESP32 返回已收字节 rx
② PC 从 rx 继续 PKG_DATA（不必重传）
③ 若 ESP32 已 STAGED（收完未转发）→ 直接可 OTA_START
```

### 6.3 ESP32↔STM32 中断（STM32 侧看门狗/掉线）

```
① ESP32 DATA 块无 ACK 超时（默认 1s，重试 3 次）
② 仍失败 → STATUS 查询实际进度 → 若 STM32 会话仍有效，从实际 rx 续传
③ 若 STATUS 也无响应 → 判定 STM32 离线 → 上报 PC（保留 ESP32 暂存，等待重试）
④ 重试上限后 → OTA_ABORT，ESTM32 侧会话由 D00 的 5s 空闲超时自动 ABORT（ota_can_svc 同款机制）
```

### 6.4 掉电恢复

| 掉电点 | 恢复行为 |
| --- | --- |
| ESP32 收包中 | 若启用 `stage_persist`：重启后 PKG_QUERY 返回已收字节；否则要求重传（PSRAM 丢失） |
| ESP32 已 STAGED、未转发 | 同上（未持久化则需 PC 重发） |
| STM32 写 ota_dl 中 | D00 会话槽（`OTA_SESSION_BASE`）自动续传 ✓ |
| STM32 解密写 RUN 中 | BOOT 状态机自愈：PENDING/魔数无效 → 回滚到 img_lib ✓ |
| STM32 已 PENDING 新固件启动失败 | BOOT 自动回滚（MAX_BOOT_TRIES=3） ✓ |

## 7. 速度设计（极致）

### 7.1 瓶颈链条逐段分析（921600 bps 基线）

| 段 | 理论 | 实际/预估 | 是否瓶颈 |
| --- | --- | --- | --- |
| ① PC → ESP32（WiFi TCP） | 10~20 Mbps | **1~2 MB/s** | 否 |
| ② ESP32 PSRAM 写入 + SHA256 | Octal PSRAM 80MHz | ~10 MB/s（SHA256 硬件加速 ~50MB/s） | 否 |
| ③ ESP32 → STM32（UART 921600） | 92 KB/s | 见下 | **⚠️ 是** |
| ④ STM32 写外部 W25Q128 | 页编程 256B/0.7ms | **~200 KB/s**（D00 TCP OTA 实测 190KB/s） | **⚠️ 是（最终瓶颈）** |

**③ 段细化（逐块 ACK 模式）**：
```
单块周期 = 240B 传输(2.6ms) + STM32 写 Flash(~1.2ms) + ACK 往返(0.1ms) + 双端处理(~0.3ms) ≈ 4.2ms
→ 吞吐 ≈ 240B / 4.2ms ≈ 57 KB/s     ← 只有理论值的 62%
```

### 7.2 六项优化手段

| # | 手段 | 收益 | 代价 |
| --- | --- | --- | --- |
| 1 | **波特率提升** 921600 → **2 Mbps**（ESP32-S3 支持 5Mbps；F407 @84MHz APB2 支持 2~3Mbps） | ③段理论 200 KB/s | 需验证信号质量（短线+共地；必要时串 33Ω） |
| 2 | **滑动窗口**（ESP32 连发 W=8 块后再收 ACK） | 隐藏 RTT，③段逼近④段 | 需 RTS/CTS 流控防 STM32 溢出 |
| 3 | **硬件流控 RTS/CTS** | 消除溢出丢帧（溢出=重传=速度崩塌） | 需 2 根额外信号线 |
| 4 | **DMA 双缓冲**（两端均已具备） | 零 CPU 搬运 | ESP32 侧需实现 UART DMA + 空闲断帧 |
| 5 | **零拷贝**（TCP 数据直落 PSRAM 目标偏移） | 省 2 次 memcpy | 需缓冲区对齐规划 |
| 6 | **包内大块（PC→ESP32 用 1KB）** | 上传段开销降 4 倍 | ESP32 侧协议设计（已在 §5.1 体现） |

### 7.3 目标吞吐预算

| 场景 | 端到端吞吐 | 300KB 包耗时 | 900KB 包耗时 |
| --- | --- | --- | --- |
| 基线（921600 + 逐块 ACK） | ~57 KB/s | 5.3 s | 15.8 s |
| 优化后（2 Mbps + 窗口 8 + 流控） | **~190 KB/s**（受④段限制） | **1.6 s** | **4.7 s** |

> 结论：**优化目标就是把③段压到④段之下（190KB/s）**，再快也无意义——因为 STM32 写外部 Flash 是硬上限。
> 若未来需要更快，只能改 D00 侧存储策略（例如减少备份/改用 QSPI），不在本方案范围。

### 7.4 加速前置条件（必须同时满足）

1. ⚠️ **D00 侧 UART 需支持 2 Mbps**：USART6 挂在 APB2(84MHz)，`BRR = 84M/2M = 42` → 可精确分频 ✅
2. ⚠️ **STM32 侧收包路径不能丢帧**：现有 `HOSTLINK_RX_DMA_BUF_SIZE=256` 需评估（窗口模式下需 ≥2KB 缓冲）
3. ⚠️ **D00 需支持"无 ACK 连发不溢出"**：靠硬件流控 + STM32 DMA 环形缓冲

## 8. 安全设计（八道防线）

| # | 防线 | 机制 | 责任方 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 无线接入 | WPA2/WPA3-PSK（ESP32 软 AP 或 STA 入网） | ESP32 | 新增 |
| 2 | 会话鉴权 | 一次性 token / 挑战-应答（`AUTH`） | ESP32 + PC | 新增 |
| 3 | 上传完整性 | 分块 CRC16（L1）+ 整包 SHA256（L2） | ESP32 | 新增 |
| 4 | 固件真实性 | **ECDSA secp256r1 验签**（板载双公钥，支持轮换） | **BOOT** | ✅ 已有 |
| 5 | 固件保密性 | **AES-256-CTR**，密钥 = `SHA256(UID‖salt)` 一机一密 | **BOOT** | ✅ 已有 |
| 6 | 防跨芯片 | `header.chip_id == DBGMCU->IDCODE` | **BOOT** | ✅ 已有 |
| 7 | 防重放 | `build_no > last_build_no` 严格递增 | **BOOT**（+ESP32 预检） | ✅ 已有 |
| 8 | 防降级 | `version ≥ 当前版本` | **BOOT**（+ESP32 预检） | ✅ 已有 |

**附加建议（可选）**：
- **ESP32 侧自身安全**：启用 Secure Boot v2 + Flash 加密（防止中继器被替换为恶意固件）——工业部署建议开
- **审计日志**：ESP32 记录每次升级（时间/来源 IP/包摘要/结果），可选上报 MQTT
- **物理防误触**：升级触发可要求"短接跳线/按键确认"（防远程未授权升级）

**信任模型**：
```
PC（私钥持有者，唯一签名源）
  └─ WiFi（加密）→ ESP32（不可信中继：可篡改？）
       └─ 但篡改会被 L2(SHA256) 与 L3(ECDSA) 双重发现 → 升级失败（不砖机）
            └─ STM32/BOOT（信任根：唯一验证者）
```
→ **即使 ESP32 完全被攻陷，攻击者也无法植入未签名固件**（无密钥）。这是把安全交给 BOOT 的核心价值。

## 9. 稳定性设计

### 9.1 会话状态机（ESP32 侧）

```
IDLE ──PKG_BEGIN──► RECEIVING ──PKG_COMMIT(SHA256✓)──► STAGED
  ▲                     │                                  │
  │                 超时/ABORT                          OTA_START
  │                     ▼                                  ▼
  └────────────────── ERROR ◄────────────────────── TRANSFERRING
                                                           │
                                          ┌────────────────┴────────────────┐
                                     STM32 END 成功                  转发失败(超限)
                                          ▼                                ▼
                                        DONE ──(回读启动确认)──► CONFIRMED   ERROR(可重试)
```

### 9.2 三级断点续传（责任划分清晰）

| 级 | 范围 | 断点存储 | 恢复决策者 |
| --- | --- | --- | --- |
| L1 | PC → ESP32 | ESP32 PSRAM/Flash（`PKG_QUERY` 返回 rx） | PC |
| L2 | ESP32 → STM32 | **D00 会话槽**（`OTA_SESSION_BASE`，1024 槽 × 32B） | ESP32（STATUS 查询） |
| L3 | STM32 安装期掉电 | BOOT 参数区 PENDING + 外部备份槽 | BOOT 状态机（自动） |

### 9.3 重试矩阵

| 层级 | 触发条件 | 动作 | 上限 |
| --- | --- | --- | --- |
| 帧级 | 无 ACK / CRC 错 | 重发该帧 | 3 次 → 上报 |
| 块级 | DATA 状态码非 0 | STATUS 对齐进度后续传 | 5 次 → 会话级 |
| 会话级 | UART 完全无响应 | 复位 STM32？→ 重连 → 重新 STATUS | 2 次 → ERROR |
| 接入级 | PC 断开 | 保留暂存（可配超时 30min） | — |

### 9.4 看门狗协同（三层）

| 层 | 机制 | 说明 |
| --- | --- | --- |
| ESP32 硬件 | IWDG/Task WDT | 长操作（SHA256/Flash 擦写）分段喂狗 |
| ESP32 任务级 | 自研任务心跳（同 D00 模式） | 定位"哪个任务卡死" |
| STM32 | 既有 IWDG（16.4s）+ 任务级看门狗 | ✅ 已有 |

### 9.5 链路监控与自愈

- **心跳**：ESP32 每 1s 发 `CMD_GET_INFO` 探测 STM32 APP 在线（既是监控，也顺带验证链路）
- **速率自适应**：连续 NAK 时自动降窗口/降波特率（可选高级特性）
- **统计上报**：速率/重传/错误计数随 `OTA_PROGRESS` 上报（工业现场可观测）

## 10. 硬件连接方案

### 10.1 方案 1（推荐）：ESP32 ↔ STM32 **USART6（PC6/PC7）**

| STM32F407 | 方向 | ESP32-S3 | 说明 |
| --- | --- | --- | --- |
| PC6 (USART6_TX, AF8) | → | GPIO (RX) | 数据 STM32→ESP32 |
| PC7 (USART6_RX, AF8) | ← | GPIO (TX) | 数据 ESP32→STM32 |
| PD4 或 PC8（**待定**） | ← | GPIO (RTS) | 硬件流控（ESP32→STM32 方向） |
| PD3 或 PC9（**待定**） | → | GPIO (CTS) | 硬件流控 |
| GND | — | GND | **必须共地** |
| 3V3 | — | 3V3 | 逻辑电平 3.3V 直连（**两侧均 3.3V，无需电平转换**） |

**要点**：
- 波特率先用 **921600** 打通，再评估 2 Mbps（线长 <15cm、共地良好时可稳定）
- 建议 TX/RX 串 **33Ω** 串阻（抑制过冲，工业环境更稳）
- 若电磁环境恶劣：加 **数字隔离器**（如 ADuM1201）或 TVS

### 10.2 方案 2（备选）：ESP32 ↔ STM32 **USART1（PA9/PA10）**

- **优点**：D00 固件**零改动**（HOSTLINK 原生口）
- **缺点**：PC 的 CH343 串口不能再直连 STM32（需拔插切换或加多路开关）
- **适用**：快速验证阶段（先用此方案打通链路，再切方案 1）

### 10.3 电源与复位协同

| 项 | 建议 |
| --- | --- |
| 供电 | ESP32 与 STM32 独立供电（各自 LDO），**仅共地**；避免大电流耦合 |
| 复位联动 | ESP32 可控制 STM32 NRST（可选）→ 用于"卡死时硬复位重试"；需加隔离/开漏 |
| STM32 模式控制 | 可选：ESP32 控制 BOOT0 → 强制进 BOOT 模式（用于 STM32 APP 完全无响应时救砖） |

| 既有资产 | 本方案如何复用 |
| --- | --- |
| D00 HOSTLINK 协议 | **原样复用**（帧格式/命令码/CRC） |
| D00 OTA Agent + 会话槽 | **原样复用**（断点续传/状态机） |
| D00 BOOT 六道安全关 | **原样复用**（信任根） |
